## Operational ordering and safety

1. **Background/UI close while service remains alive:** existing live MediaSession wins; P11 restore only occurs once per newly created service with empty live queue, never during `onResume()` or as a second queue source.
2. **Cold start:** Android creates the one `MusicCopilotApplication` store and service's one player/session; service asynchronously reads existing Proto **without an automatic `Play` command**. All refs rechecked against current MediaStore/OS permission. A fresh private or system MediaController command received mid-read increments a generation, canceling restoration before it can touch the Player. Absence of a checkpoint simply leaves No Track.
3. **Checkpoint content:** schema=1, queue revision, positional list of opaque MediaStore refs, current occurrence, nonnegative current position and epoch. No URLs, raw paths, titles, album/artist data, audio, cloud, stream, device ID or force-stop intent. DataStore atomic `updateData` plus serialized writer; fresh ID-length check (≤128), count bound (≤5000), schema guard. Invalid/future schema is rejected with no player queue manipulation, and future schema is not rewritten merely because a read failed.
4. **Missing media:** missing nonselected entries dropped in original order, selected-missing falls back to first accessible local item at position 0. Permission loss aborts recovery entirely. A second fresh P04 preflight rejects further selected-file loss; no unvalidated URI is replayed and no network fallback exists.
5. **Paused only:** `playWhenReady=false`, `prepare()`, `pause()` are the only cold Player actions. MediaSession standard metadata and queue state are derived from the actual Media3 Player, not directly from the Proto snapshot. Only a **new explicit** Play can start sound after restore. Restoration is P1; it is NOT process-death audio continuation.
6. **Explicit Stop:** cancels persisted intent by clearing snapshot and suppressing incidental stopped-Player timeline events. Position/queue changes and entering Paused are saved; real Playing writes at 5-second intervals without UI ownership. The 5s cadence is a retained ADR-0007 requirement, not a phone test result.
7. **Known technical risk for P12/P13:** Immediate Pause/Stop followed by immediate MediaSessionService destruction may cancel a service-scoped pending DataStore write before it completes. `updateData` is atomic if completed, but completion across abrupt process kill/force-stop is NOT guaranteed. P12 must review possible application-scope write handoff or bounded shutdown flush if necessary; only the final APK/actual field evidence can establish M33 reliability. Likewise 5,000-item revalidation could exceed the app controller's existing 10-second request timeout (P12 technical debt). No success claim beyond code/source audit.
8. **Android force-stop:** force-stop kills active playback. On later ordinary app launch, a valid **P1 checkpoint may restore Paused**. P0 does not promise surviving force-stop, caller app process death or OEM restrictions.
9. **Interaction with P10:** corrupt/error snapshots are not checkpointed; a missing verified media reference is not re-added simply because an old checkpoint says it existed. Restoration never bypasses the route-loss/manual-Pause safeguards.
